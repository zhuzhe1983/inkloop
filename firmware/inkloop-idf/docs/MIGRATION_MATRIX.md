portable/host test exists and the implementation is in the stated ESP-IDF
component graph. It never means the behavior has run on a C151. The current
`0.4.0-beta.28` source candidate passes the complete repository suite 403/403,
lint with zero errors, and clean official ESP-IDF v6.0.2 C151/mock links. The
C151 application SHA-256 is
`cd9498e006693b7b3ea61c143dbd230f61873f9f1a0d41a5dff020327f14091a`;
the mock-SKU application SHA-256 is
`daf5af6db451c44c620670a325ebefe747216471119c268089927b9283ffe4be`.
beta28 is a digital candidate only. beta27 has a retained inactive-slot boot
and Recovery-path physical pass, but Product remains blocked by the explicit
TF index choice. These facts do not constitute a physical release.

Every physical/live cell remains `PENDING` until an evidence bundle from
[C151_PHYSICAL_ACCEPTANCE.md](C151_PHYSICAL_ACCEPTANCE.md) records the device,
image hash, serial log, observations and verdict. No row is globally complete
while that cell is pending.

## Evidence rules

1. Source presence or a host test can establish only digital behavior.
2. An IDF build establishes compile/link and image layout, not electrical,
   radio, audio, panel, filesystem or public-service behavior.
3. A physical/live result must identify the C151, firmware SHA-256, toolchain,
   test network/service, timestamp and retained artifact; otherwise it stays
   `PENDING`.
4. No automatic erase/format, MyAI server mutation, private signing key or
   production deployment is authorized by this matrix.
5. If a test and the device disagree, the device observation fails the row and
   the discrepancy becomes a tracked defect; documentation never upgrades the
   result by inference.
